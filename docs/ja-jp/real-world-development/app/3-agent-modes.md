プロジェクトに小さな機能を追加しました。より大きな変更には、さらにしっかりしたプロセスが必要です。GitHub Copilot app は組織の既存のフローに沿って作業し、適切なものを適切な方法で構築できるように設計されています。このレッスンから数回にわたり、一般的なエージェント主導の開発プロセスに取り組みます。まず issue を使って新機能を作成し、コードが有効で機能が期待どおりに動作することを確認してから、プロジェクトにマージします。

> [!NOTE]
> 機能ワークフローを続ける間、同じセッションを使います。通常はファイルの種類ごとに異なるセッションや PR を使いますが、ここでは中心的な概念に集中するため簡略化します。

このレッスンでは、次のことを行います。

- GitHub issue から新しいエージェント セッションを開始します。
- **Plan** モードで要件を定義します。
- **Autopilot** モードで新しい機能を実装します。
- コードをレビューします。
- ブラウザー Canvas で機能を手動検証します。

この機能の作業を続けながら、リポジトリの指示を更新し、既存の quality-checks スキルをカスタマイズし、MCP による検証を追加して QA エージェントを作成し、機能 PR を作成します。

## シナリオ

Tailspin Toys のカタログが増えてきたため、訪問者がカテゴリや発行元でゲームを絞り込めるようにします。バックログの issue には機能が記載されていますが、カテゴリを組み合わせる方法など、コーディング前に合意が必要な詳細もあります。Plan モードで決定し、範囲を絞った実装を Autopilot に許可します。

## 背景

AI コーディング エージェントを開発フローに導入しても基本は変わりません。むしろ、基本はさらに重要になります。多くの開発者は、次のような流れで作業します。

1. 必要な作業の詳細が記載された issue を開きます。
2. 作成する内容の計画を立てます。
3. コードを作成してレビューします。
4. テストを実行してコードを検証します。
5. 新しい機能を手動で検証します。
6. プルリクエスト (PR) を作成します。
7. コードレビューと継続的インテグレーションが成功したら、コードをマージします。

> [!NOTE]
> 詳細な進め方はチームや組織によって異なりますが、多くは上記の流れに近いものです。

この標準的な進め方を守ることで、AI が生成したコードが要件を満たし、手作業で書いたコードと同じ検証を受けるようにできます。

## セッション モード

**セッション モード**は、エージェントにどの程度の自律性を与えるかを制御します。プロンプト フィールド下のドロップダウンから設定し、いつでも変更できます。

- **Interactive**: 開発者とエージェントが協力して作業します。エージェントは変更を提案し、次に進む前に入力を待ちます。
- **Plan**: エージェントが最初に計画を作成します。実行前に計画をレビューして承認します。
- **Autopilot**: エージェントは完全に自律してコードを書き、テストを実行し、入力を待たずに反復します。

Plan モードで開始し、計画をレビューしてから、Autopilot で実装します。

## issue からセッションを開始する

開始前に、星評価の PR がマージされ、ローカルの `main` が最新であることを確認します。

1. サイドバーの **Sessions** で Tailspin Toys のリポジトリ フォルダーを選択し、リポジトリ上部のナビゲーションで **Issues** を選択します。**Allow users to filter games by category and publisher** を開きます。テンプレートに含まれる既存の issue なので、新しく作成する必要はありません。
2. **New session** を選択し、更新済みの `main` を基にした **new working tree** を選びます。

   ![GitHub Copilot app の issue ビューで New session ボタンを矢印で示した画面](../../../_images/app-new-session-from-issue.png)

3. issue がセッションに添付されていることを確認し、モード選択で **Plan** を選びます。

> [!NOTE]
> Node.js または npm が見つからない場合は、エージェントに `node --version` と `npm --version` の実行を依頼します。普段のターミナルでは動作するのにセッションでは動作しない場合は、アプリの PATH またはバージョン マネージャーの設定を確認し、アプリを完全に終了して再起動します。失敗した操作とチェックを再試行してください。エージェントが npm を見つけられないという理由だけで npm を再インストールしないでください。

## フィルタリング機能を計画する

Copilot がコードを書く前に、実装方法を確認できるように計画を立てます。issue から開始したため、Copilot は機能要求をすでにコンテキストに含めています。次のプロンプトを送信します。

```plaintext
Build this feature.
```

Copilot の質問に回答し、計画を issue の受け入れ基準と照らし合わせます。カテゴリと発行元によるフィルタリング、アクセシブルなコントロール、データアクセスの変更、テストが含まれていることを確認します。複数カテゴリの組み合わせ方や一致するゲームがない場合の動作など、不明確な点について話し合います。

計画には、既存のプロジェクト ツールを使った lint、単体テスト、エンドツーエンド (E2E) テスト、型チェックを含めます。フィルタリングの実装とテストに範囲を絞り、品質ワークフローを完了してから PR を作成します。計画の修正は承認前に依頼し、後で検証できるよう issue の URL と合意した明確化事項を控えておきます。

## Autopilot を明示的に承認する

計画に問題がなければ、**Approve and implement this plan** または使用中のバージョンで表示される同等の選択肢を選びます。承認によってモードも切り替わると決めつけず、モード表示が **Autopilot** になっていることを確認します。

Copilot が実装を開始します。定めた計画に沿って反復し、コードを生成してテストも実行します。

> [!NOTE]
> 承認すると実装がすぐに始まる場合があります。まず計画をレビューしてください。Copilot が依存関係の不足やポートの競合を報告した場合は、チェック完了と判断する前にセットアップの問題を解決します。停止してよいのは、自分で起動したサーバーだけです。

## 実装をレビューして検証する

生成されたコードは、ほかのコードと同じようにマージ前にレビューします。コードを確認し、サイトを実行して動作も確かめます。

1. **Changes** を開き、フィルタリングの実装とテストを確認します。
2. 複数カテゴリや発行元の組み合わせも含め、結果を issue と承認した明確化事項に照らし合わせます。変更が既存のリポジトリ指示に従うことも確認します。
3. lint、単体テスト、E2E テスト、型チェックの出力を確認します。スキップされたチェックは成功ではありません。
4. 実装を承認する前に失敗を解消し、該当するチェックを再実行します。Playwright の E2E 設定はビルドしてプレビューを配信し、ローカル サーバーを再利用できます。テスト対象が以前のレッスンではなく、この worktree のサーバーであることを確認します。

## 新しい機能を試す

コードに問題がないように見えても、実際に動くでしょうか。前と同じようにアプリを起動し、ブラウザー Canvas でサイトを開きます。

1. 次のプロンプトで、アプリを起動してブラウザー Canvas で開くよう Copilot に依頼します。

   ```plaintext
   Start the app and open it in the browser canvas.
   ```

2. しばらくするとアプリが起動し、Copilot app 内にブラウザー ウィンドウが開きます。
3. カテゴリを選択し、結果がカテゴリに一致することを確認します。フィルターを解除してから発行元を選び、結果がその発行元に一致することを確認します。
4. カテゴリと発行元を組み合わせ、issue と承認済みの計画に照らして結果を確認します。複数カテゴリに対応する場合は、合意した組み合わせの動作を確認します。
5. 該当するゲームがない組み合わせを試し、空の状態を確認します。フィルターを解除またはリセットして一覧全体が戻ることも確認します。
6. 確認が終わったら、次のプロンプトで、このセッションで起動した開発サーバーを停止するよう Copilot に依頼します。

   ```plaintext
   Stop the dev server and close the browser canvas.
   ```

## 次のレッスンのためにセッションを保持する

フィルタリングの PR はまだ作成またはマージしないでください。レッスン 4 から 8 まで、このセッション、worktree、ブランチを使います。次はカスタム指示をフィルタリングのコードに適用し、スキルと QA の改善を追加してから、レッスン 8 で PR をまとめて作成してマージします。開発サーバーを停止したらセッションをそのままにし、次のレッスンで同じセッションに戻ります。
